**Create commands/forge.md** — the `/seraphim:forge [phase-id]` command.

Frontmatter:
```yaml
description: "Run the Forge phase — execute blueprint tasks one by one with progress tracking"
argument-hint: "[phase-id]"
allowed-tools: ["Read", "Write", "Bash", "Edit", "Glob", "Grep"]
```

Command body instructs Opus to:

1. **Resolve project root and phase-id**.

2. **Check prerequisite**: Read `.seraphim/phases/{phase-id}/blueprint.md`. Must exist. Parse SERAPHIM:BLUEPRINT marker to extract `project_type` and `task_count`. Parse SERAPHIM:TASK markers to get the task list.

3. **Read config** and resolve model for `forge` phase slot.

4. **Record profile audit**: Write `profile_at_execution.forge` and `model_at_execution.forge` to state.json BEFORE execution.

5. **Initialize forge-log.md**: Create the file with PHASE_START marker and header.

6. **Execute tasks sequentially** — for each TASK marker in blueprint:

   a. **Branch on project_type** (per D-01, D-03):
      - `code`: Instruct model to write/modify source code files as specified in the task. The model should produce the actual file changes.
      - `research` / `writing`: Instruct model to write a prose .md file per blueprint task — one output file per task, committed to the project directory like code (per D-01).
      - `science`: Instruct model to write analysis scripts and results .md files.
      - `mixed`: Read the per-task `type` attribute from SERAPHIM:TASK marker and branch per task.

   b. **Dispatch or inline**: Same Opus-inline vs CLI-dispatch pattern as other commands. For Codex (the default Performance forge model), dispatch via CLI with a prompt containing: the task spec from blueprint, the project_type, relevant existing file contents, and instructions.

   c. **Write per-task entry to forge-log.md**: After each task completes, append:
      ```
      ### Task {id}: {name}
      <!-- SERAPHIM:FORGE_TASK id="task-N" status="complete|failed" -->
      - Model: {model}
      - Files modified: [list]
      - Output summary: [brief]
      ```

   d. **Do NOT auto-commit** (per Pitfall 7 and Open Question 2 from research). Display the diff after each task. Phase 4 adds checkpoint.js and commit-after-checkpoint logic. In Phase 3, Forge writes files and logs but leaves commits to the human or to Phase 4's checkpoint gate.

   e. **On task failure**: Log the failure in forge-log.md with `status="failed"` and the error message. Do NOT retry in Phase 3 — retry logic is Phase 4 (QUAL-02). Continue to next task or stop depending on whether the next task depends on the failed one.

7. **Finalize forge-log.md**: Append PHASE_COMPLETE marker with task completion counts.
   ```
   <!-- SERAPHIM:PHASE_COMPLETE tasks_total="N" tasks_complete="M" tasks_failed="F" -->
   ```

8. **Print Wing V banner** with task completion stats (N/M complete, F failed) and cost.

**Create commands/crucible.md** — the `/seraphim:crucible [phase-id]` command.

Frontmatter:
```yaml
description: "Run the Crucible phase — verification pass and adversarial break attempt"
argument-hint: "[phase-id]"
allowed-tools: ["Read", "Write", "Bash", "Glob", "Grep"]
```

Command body instructs Opus to:

1. **Resolve project root and phase-id**.

2. **Check prerequisite**: Read `.seraphim/phases/{phase-id}/forge-log.md`. Must exist. If missing, abort: "Crucible requires Forge output. Run /seraphim:forge {phase-id} first."

3. **Read config**, resolve `project_type` from config (or from the BLUEPRINT marker in blueprint.md).

4. **Record profile audit**: Write `profile_at_execution.crucible_verify` and `profile_at_execution.crucible_adversarial` plus corresponding model entries to state.json BEFORE execution.

5. **Check loop cap**: Read state.json loops.crucible_forge. If at or above config.max_loops, halt with message similar to judge's loop cap halt.

6. **Pass 1: Verification** — resolve model for `crucible_verify` phase slot.

   Branch on project_type (per D-02):
   - `code`: Goal-backward verification — does the code fulfill every blueprint task's success criteria? Check: tests pass, imports resolve, no stub functions, key behaviors implemented. Read blueprint.md success criteria and verify each one.
   - `research` / `writing`: Completeness check — does the output cover ALL blueprint sections? Are there gaps, missing arguments, unsupported claims? (per D-02)
   - `science`: Methodology check — is the methodology sound? Could results be replicated? Are statistical claims valid?

   Dispatch or inline per the standard Opus-check pattern. Write verification results to a temp section.

7. **Pass 2: Adversarial** — resolve model for `crucible_adversarial` phase slot (typically MiniMax).

   Branch on project_type (per D-02):
   - `code`: Adversarial break attempt — try to find bugs, security holes, race conditions, edge cases that crash the code. Think like an attacker.
   - `research` / `writing`: Simulated critical peer review — poke holes in arguments, find logical gaps, identify unsupported claims, challenge methodology (per D-02).
   - `science`: Replication critique — challenge experimental design, sample sizes, confounding variables, alternative explanations.

   Dispatch via CLI (MiniMax is always external). Write adversarial results to a temp section.

8. **Combine into crucible.md**:
   ```
   <!-- SERAPHIM:PHASE_START phase="crucible" model_verify="..." model_adversarial="..." profile="..." timestamp="..." -->
   
   # Crucible Report
   
   ## Verification Pass
   <!-- SERAPHIM:CRUCIBLE_VERIFY result="pass|fail" issues_found="N" -->
   [Verification analysis — what passed, what failed]
   
   ### Issues Found
   [List of verification failures, if any]
   
   ## Adversarial Pass
   <!-- SERAPHIM:CRUCIBLE_ADVERSARIAL result="pass|fail" vulnerabilities_found="N" -->
   [Adversarial analysis — what was tried, what broke]
   
   ### Vulnerabilities Found
   [List of adversarial findings, if any]
   
   ## Overall Verdict
   <!-- SERAPHIM:PHASE_COMPLETE verdict="pass|fail" verify_result="pass|fail" adversarial_result="pass|fail" total_issues="N" -->
   [Summary — overall pass/fail with reasoning]
   ```

   Overall verdict is `pass` only if BOTH passes are `pass`. Any failure means `fail`.

9. **Print Wing VI banner** with overall verdict, issue count, and cost (combined cost of both passes).
