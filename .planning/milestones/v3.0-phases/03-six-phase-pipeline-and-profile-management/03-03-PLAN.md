**Create commands/judge.md** — the `/seraphim:judge [phase-id]` command.

Frontmatter:
```yaml
description: "Run the Judge phase — adversarial stress-test of all envision approaches"
argument-hint: "[phase-id]"
allowed-tools: ["Read", "Write", "Bash"]
```

Command body instructs Opus to:

1. **Resolve project root and phase-id** (same pattern as discover/envision).

2. **Check prerequisite**: Read `.seraphim/phases/{phase-id}/vision.md`. Must exist. If missing, abort: "Judge requires Envision output. Run /seraphim:envision {phase-id} first."

3. **Read config and resolve model** for `judge` phase slot.

4. **Record profile audit**: Write `profile_at_execution.judge` and `model_at_execution.judge` to state.json BEFORE execution (per Pitfall 3).

5. **Check loop cap** (per Pitfall 4): Read state.json loops.judge_envision. If at or above config.max_loops, halt: "Judge-Envision loop cap reached ({count}/{max}). Human resolution required. Review judgment.md and vision.md, then either: (a) reset loop counter with /seraphim:run --reset-loops, or (b) manually edit vision.md to fix approaches."

6. **Conditional dispatch**:
   - If resolved model is `claude-opus-4-6`: Opus performs the judging directly. Read vision.md, identify each approach, stress-test for fatal flaws, implementation risks, scalability concerns, security issues. Write judgment.md directly.
   - Otherwise: Write prompt to `/tmp/seraphim-judge-prompt.txt` containing the full vision.md content and judging instructions. Dispatch via CLI to the resolved model (e.g., Gemini Flash in Performance). Write output to judgment.md.

7. **Output format for judgment.md** — MUST include machine-readable markers (PIPE-03, PIPE-07):
   ```
   <!-- SERAPHIM:PHASE_START phase="judge" model="..." profile="..." timestamp="..." -->
   
   # Judgment Report
   
   ## Approach 1: {name}
   <!-- SERAPHIM:APPROACH id="approach-1" verdict="SURVIVES" -->
   [Stress test analysis, strengths found, risks assessed]
   
   ## Approach 2: {name}
   <!-- SERAPHIM:APPROACH id="approach-2" verdict="FATAL_FLAW" reason="description_of_flaw" -->
   [Why this approach fails, specific failure scenario]
   
   ## Approach 3: {name}
   <!-- SERAPHIM:APPROACH id="approach-3" verdict="CONDITIONAL" condition="what_must_be_true" -->
   [Analysis, conditions under which it could work]
   
   <!-- SERAPHIM:PHASE_COMPLETE survivors="N" fatal="N" conditional="N" loop_required="false" -->
   ```

   The `loop_required` field in PHASE_COMPLETE is `"true"` only when ALL approaches received FATAL_FLAW (survivors=0 and conditional=0). This signals Phase 4's feedback loop logic.

8. **Validate output**: After writing judgment.md, parse it with markers.js to confirm at least one SERAPHIM:APPROACH marker exists. If the model produced no markers, re-prompt or abort with error — do NOT write an unparseable file (per anti-pattern from research).

9. **Print Wing III banner** with verdict summary (N survived, N fatal, N conditional) and cost.

The judge prompt must instruct the model to:
- Be adversarial — actively try to break each approach
- Look for: scalability bottlenecks, security vulnerabilities, maintenance nightmares, hidden complexity, dependency risks, edge cases
- Use EXACTLY the verdict values: SURVIVES, FATAL_FLAW, or CONDITIONAL (no variations)
- Include the `reason` attribute on FATAL_FLAW and the `condition` attribute on CONDITIONAL
- Be specific in reasoning — not "this might fail" but "concurrent writes to the session file cause data corruption because writeFileSync is not atomic across processes"

**Create commands/architect.md** — the `/seraphim:architect [phase-id]` command.

Frontmatter:
```yaml
description: "Run the Architect phase — create a detailed blueprint from the top surviving approach"
argument-hint: "[phase-id]"
allowed-tools: ["Read", "Write", "Bash", "Glob", "Grep"]
```

Command body instructs Opus to:

1. **Resolve project root and phase-id**.

2. **Check prerequisite**: Read `.seraphim/phases/{phase-id}/judgment.md`. Must exist. Parse SERAPHIM:APPROACH markers. At least one must have `verdict="SURVIVES"` or `verdict="CONDITIONAL"`. If none survive, abort: "No approaches survived the Judge phase. Run /seraphim:envision {phase-id} to generate new approaches, then /seraphim:judge {phase-id} again."

3. **Select top approach**: Pick the first SURVIVES approach. If only CONDITIONAL approaches exist, pick the first one and note the condition in the blueprint.

4. **Read config** and resolve model for `architect` phase slot.

5. **Record profile audit**: Write `profile_at_execution.architect` and `model_at_execution.architect` to state.json BEFORE execution.

6. **Read project_type from config** (per D-03). This goes into the BLUEPRINT marker.

7. **Conditional dispatch**:
   - If resolved model is `claude-opus-4-6`: Opus creates the blueprint directly. Read the selected approach from judgment.md, the full discovery files, and the original vision.md for context. Produce a detailed blueprint.
   - Otherwise: Write prompt with all context (selected approach, discovery, judgment) and dispatch via CLI.

8. **Output format for blueprint.md** — MUST include BLUEPRINT marker with project_type (PIPE-10):
   ```
   <!-- SERAPHIM:PHASE_START phase="architect" model="..." profile="..." timestamp="..." -->
   <!-- SERAPHIM:BLUEPRINT project_type="code" phase="{phase-id}" task_count="N" -->
   
   # Blueprint: {approach name}
   
   ## Overview
   [High-level description of the approach and why it was selected]
   
   ## Architecture
   [Component structure, data flow, key interfaces]
   
   ## Tasks
   
   ### Task 1: {name}
   <!-- SERAPHIM:TASK id="task-1" type="code|prose|analysis" -->
   - **Files**: [specific file paths]
   - **Description**: [what to build]
   - **Dependencies**: [what must exist first]
   - **Test criteria**: [how to verify this task is done]
   
   ### Task 2: {name}
   <!-- SERAPHIM:TASK id="task-2" type="code|prose|analysis" -->
   ...
   
   ## Success Criteria
   [Measurable conditions for blueprint completion]
   
   <!-- SERAPHIM:PHASE_COMPLETE task_count="N" project_type="code" -->
   ```

   The `type` attribute on TASK markers enables Forge to branch per-task for mixed project types.

9. **Print Wing IV banner** with task count and project type.

The architect prompt must instruct the model to:
- Create a concrete, executable task breakdown (not vague "implement X")
- Each task must have specific file paths, not "the relevant files"
- Include test/verification criteria per task
- Include the project_type in BLUEPRINT marker (read from config.json)
- For non-code projects (research, writing, science): tasks describe documents to produce, analysis to perform, or experiments to run — each task still has a specific output file
- Task dependencies must form a valid DAG (no circular deps)
