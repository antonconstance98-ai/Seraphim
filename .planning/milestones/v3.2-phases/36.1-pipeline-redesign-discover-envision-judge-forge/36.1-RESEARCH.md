## User Constraints (from CONTEXT.md)

### Locked Decisions

**Discover (Wing I)**
- D-01: Uses Perplexity + SearXNG for real web research. No fake or training-data-only URLs.
- D-02: Rounds are broad → focused, no hard cap. Human can go deeper, pivot, or rabbit-hole. No fixed round limit.
- D-03: After each round, AI presents findings + explicit prompt: "Go deeper / New direction / I'm armed, move to Envision." Human always chooses.
- D-04: Interesting links accumulate across rounds. At the end, AI + human collaboratively filter to final 5-7 high-importance links (articles, Twitter threads, YouTube, podcasts, docs).
- D-05: Bad search results: AI auto-retries once with refined query. If still poor, surfaces issue and asks human for direction.
- D-06: Final output: `discovery.md` with research findings + curated 5-7 links. Arms the human for Envision.

**Envision (Wing II)**
- D-07: Envision is CONVERGENT. Narrows scattered discovery into ONE solid unified project vision. Not multiple alternatives — one clear direction.
- D-08: Scientific approach to narrow abstract thoughts: categorize inputs, identify themes, surface conflicts, resolve tensions, distill into clear statements.
- D-09: Requires its own research to fill knowledge gaps discovered during convergence.
- D-10: AI proposes 6-10 discussion topics derived from discovery. Human reorders, adds, or removes topics before discussion starts.
- D-11: Each topic discussed conversationally. After each topic, AI evaluates whether there's enough clarity to write the vision. When threshold hit, offers to draft.
- D-12: Output: `vision.md` containing project goals, what it does, how it does it, constraints, aspirations, notes, and general outline plan. ONE vision, not alternatives.

**Judge — Pass 1: Vision Review**
- D-13: Judge reviews `vision.md` and surfaces things that might need tweaking — gaps in logic, unrealistic assumptions, missing constraints, internal contradictions.
- D-14: LIGHT pass — not adversarial. Judge is helping refine, not trying to kill the vision.
- D-15: Each suggested tweak presented to human who approves or disapproves individually. Human has final say on every change.
- D-16: Output: Updated `vision.md` (tweaks applied directly). Vision is now final and approved.

**Architect (Wing IV)**
- D-17: Architect reads FINAL `vision.md` — NOT `judgment.md`. Vision is the spec.
- D-18: Architect creates 3 different technical build plans/approaches. Same goal, different technical paths.
- D-19: AI decides plan count based on complexity (2-4 range: simple=2, medium=3, complex=4). Default is 3.
- D-20: Each plan covers architecture, tech stack choices, component structure, data model, implementation strategy.

**Judge — Pass 2: Architecture Review**
- D-21: Judge reviews Architect's technical plans. IS adversarial — stress-testing each approach.
- D-22: Judge either: (a) picks the best winner, (b) merges winning aspects from multiple plans, or (c) gives harder rules/parameters and sends back to Architect (max 1 loop).
- D-23: Output: ONE `blueprint.md` — final merged/selected technical plan.
- D-24: `blueprint.md` must be written so precisely that even a local LLM can follow it blindly.
- D-25: `blueprint.md` is broken into build phases with their own build waves (GSD-style structure).

**Forge/Executor (Wing V)**
- D-26: Forge reads `blueprint.md` and executes each build phase sequentially.
- D-27: For EACH build phase, Forge runs full GSD cycle: Research → Discuss → Plan → Execute → Verify.
- D-28: Each phase spawns separate agents with brand new context. No context bleed between build phases.
- D-29: Forge does NOT re-decide architecture. Grey area discussions are about implementation details only.

**Autonomous Mode Lockout**
- D-30: Autonomous mode cannot be enabled until Envision is complete (vision.md exists and has been Judge-approved). Refusal message: "Autonomous mode blocked. Discover and Envision need human input — without it you get a pure AI project. Use --skip-human-gates if you really want that."
- D-31: Override via `--skip-human-gates` flag. Loud warning but allows it.
- D-32: With autonomous mode on, Forge's per-phase grey area discussions are skipped (auto-selected).

**Pipeline Orchestrator (run.md)**
- D-33: New phase sequence: Discover → Envision → Judge(vision) → Architect → Judge(architecture) → Forge → Crucible.
- D-34: Judge needs `--mode` parameter: `--mode vision` for Pass 1 (light review), `--mode architecture` for Pass 2 (adversarial + blueprint creation).
- D-35: Architect→Judge→Architect loop (max 1) managed by `run.md`, not Judge itself.

## Summary

This phase rewrites five of the six Seraphim pipeline command files and updates the run.md orchestrator. The redesign is not about new infrastructure — all required lib files (markers.js, dispatch.js, phase-state.js, wave-planner.js, research-tracker.js) are reused unchanged. The work is entirely in the command .md files and the prompt/logic they contain.

The two most significant conceptual changes are: (1) Envision flips from divergent (3-5 alternatives) to convergent (one unified vision), and (2) Judge runs twice with different personalities — a light collaborative pass on the vision, then an adversarial stress-test on the architecture. The Forge becomes a GSD-style orchestrator, running a full research→discuss→plan→execute→verify cycle per build phase rather than executing blueprint tasks one by one.

The autonomous mode lockout gate is a new guard added to `run.md` — it blocks execution until `vision.md` exists and has been Judge-approved, enforcing human involvement through Envision.

**Primary recommendation:** Plan this as six discrete file rewrites. Each command file is self-contained. The only cross-file coordination points are: (1) Judge's `--mode` parameter (affects both judge.md and run.md), (2) Architect reading vision.md instead of judgment.md, and (3) Forge's new multi-phase GSD structure reading blueprint.md differently.

Output file changes (new vs old):

|---|---|---|

### Pattern 1: Conversational Round Loop (Discover)

The new Discover is a human-in-the-loop conversation loop rather than a one-shot parallel dispatch. The pattern is:

```
while human wants to continue:
    1. Run search round (Perplexity + SearXNG)
    2. Present findings + accumulate interesting links
    3. If search results poor → auto-retry once with refined query; if still poor → ask human
    4. Present 3 options: go deeper / new direction / move to Envision
    5. Human chooses
on exit:
    6. Present all accumulated links, collaborate to filter to 5-7
    7. Write discovery.md (findings summary + curated links)
```

This is a fundamental shift from the current parallel 4-track dispatch model. The new Discover is interactive, not batch.

### Pattern 2: Convergent Narrowing (Envision)

The new Envision runs a structured conversation to converge on one vision, not generate alternatives:

```
1. Read discovery.md
2. AI generates 6-10 discussion topics from discovery material
3. Human reorders/adds/removes topics
4. For each topic: discuss conversationally; AI tracks clarity level
5. When clarity threshold hit: offer to draft vision
6. Fill knowledge gaps via research if needed (uses research-tracker pattern)
7. Write vision.md (ONE vision — goals, approach, constraints, aspirations, outline)
```

The output format for vision.md is entirely new. No APPROACH markers. The document is a structured vision spec, not a list of alternatives.

### Pattern 3: Two-Pass Judge with --mode Flag

Judge receives `--mode vision` or `--mode architecture` as a CLI argument. The dispatch happens via the same `judge` slot in profiles.json, but the behavior diverges completely:

```
--mode vision:
  Input: vision.md
  Behavior: light review, surface tweaks as suggestions
  Human loop: approve/disapprove each tweak individually
  Output: updated vision.md (in-place edit)

--mode architecture:
  Input: architect-plans.md (2-4 technical plans)
  Behavior: adversarial stress-test each plan
  Decision: pick winner / merge aspects / send back to Architect (max 1 loop)
  Output: blueprint.md (ONE precise execution spec)
```

The `--mode` parameter must be extracted from `$ARGUMENTS` in judge.md Step 1. The `run.md` orchestrator passes `--mode vision` before Architect, and `--mode architecture` after Architect.

### Pattern 4: Architect Produces N Plans (not 1)

The current Architect picks the best surviving approach from judgment.md and produces one blueprint. The new Architect:

1. Reads `vision.md` (not judgment.md — vision is now the approved spec)
2. Produces 2-4 distinct technical plans based on complexity assessment
3. Writes `architect-plans.md` (new output file)
4. Does NOT produce `blueprint.md` — that's now Judge Pass 2's job

The SERAPHIM marker structure in `architect-plans.md` needs new plan-level markers. Recommendation: use `SERAPHIM:PLAN id="plan-1"` markers analogous to the current `SERAPHIM:APPROACH` markers. This lets Judge Pass 2 parse them using the existing markers.js `parseMarkers` function.

### Pattern 5: Forge as GSD Orchestrator

The new Forge is fundamentally different. It reads `blueprint.md` where the blueprint now contains BUILD PHASES (not atomic tasks). For each build phase:

```
1. Research  → spawn research subagent for this phase's technical domain
2. Discuss   → surface grey areas to human; lock implementation decisions
3. Plan      → create detailed task plans with acceptance criteria
4. Execute   → run tasks in waves (wave-planner.js Kahn's algorithm)
5. Verify    → verify phase completion against success criteria
```

The existing `wave-planner.js` `resolveWaves()` function handles step 4's wave decomposition. The `research-tracker.js` pattern handles step 1's research state. Steps 2-3 mirror GSD's `discuss.md` + `plan.md` commands.

### Anti-Patterns to Avoid

- **Modifying markers.js for new marker types:** The existing `emitMarker(type, attrs)` already supports any type string. New markers (PLAN, BUILD_PHASE, VISION, etc.) require no lib changes — just use `emitMarker` with new type names directly in the command files.
- **Rewriting dispatch.js for the --mode flag:** The `--mode` flag is a prompt parameter, not a model routing parameter. Pass it as context in the prompt, not as a new dispatch argument.
- **Making Envision check for autonomous mode:** The autonomous lockout belongs only in `run.md`. Individual command files should not contain the lockout logic — they must remain independently invocable.
- **Using the old `judgment.md` as Architect's input:** D-17 is explicit: Architect reads `vision.md`. The judgment step now updates `vision.md` in place. There is no `judgment.md` for the vision review.
- **Reusing the old SERAPHIM:APPROACH marker for Architect plans:** The old APPROACH marker is tied to Judge's verdict system (SURVIVES/FATAL_FLAW/CONDITIONAL). The new Architect output is not being judged for survival — it's being stress-tested for implementation quality. Use SERAPHIM:PLAN markers to avoid confusing the marker semantics.

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Marker parse/emit | Custom regex in new commands | `lib/markers.js` `parseMarkers`, `emitMarker` | Already handles quoting, attributes, multiline |

| Atomic file writes | Direct `fs.writeFileSync` | `tmp + fs.renameSync` pattern (as in research-tracker.js) | Prevents partial writes from corrupting state files |

## Common Pitfalls

### Pitfall 1: vision.md format collision between old and new Envision

**What goes wrong:** If any code (Crucible, run.md verification, state checks) reads `vision.md` expecting old APPROACH markers, it will break after the new Envision writes a vision spec without them.

**Why it happens:** The old Judge reads APPROACH markers from vision.md to determine verdicts. The new Judge Pass 2 reads PLAN markers from `architect-plans.md`. If run.md still tries to verify vision.md by checking for APPROACH markers, it fails.

**How to avoid:** Update run.md output verification table to expect the new output files per phase. Remove any APPROACH marker checks from the vision.md verification step. The new vision.md is a pure prose document; verify it by checking for PHASE_COMPLETE with `phase="envision"`.

### Pitfall 2: Judge --mode not parsed causes both passes to run identical logic

**What goes wrong:** If judge.md Step 1 doesn't correctly extract `--mode vision` vs `--mode architecture`, both passes run the same behavior (defaulting to adversarial or defaulting to light).

**How to avoid:** In judge.md, extract `--mode` as a required argument. If absent, default to `--mode architecture` for backward compatibility (the current behavior). Emit the mode into the PHASE_START marker so it's auditable: `phase="judge" mode="vision"`.

### Pitfall 3: Architect→Judge loop managed in judge.md instead of run.md

**What goes wrong:** D-35 explicitly states the loop is managed by run.md. If judge.md tries to invoke architect.md directly, it breaks the command independence principle and creates circular command invocation.

**How to avoid:** judge.md writes `architect-plans.md` OR writes `blueprint.md` based on its decision. It emits a marker with `loop_required="true"` if it's sending back to Architect. run.md reads this marker and re-invokes architect if needed (max 1 loop via state.loops counter).

### Pitfall 4: Forge spawning subagents with context bleed

**What goes wrong:** If the Forge passes discovery.md + vision.md + previous build phases' output to each new agent, later build phases get massive context and earlier decisions leak into supposedly fresh execution contexts.

**How to avoid:** D-28 specifies brand new context per build phase. Each agent spawned by Forge receives ONLY: the specific build phase spec from blueprint.md, and whatever files/context that phase's research step identifies as relevant. No cumulative context injection.

### Pitfall 5: Autonomous lockout in individual commands rather than only run.md

**What goes wrong:** If discover.md or envision.md contain the lockout logic, invoking them standalone (not via run.md) fails when the user hasn't completed the pipeline, even for legitimate standalone use.

**How to avoid:** The lockout is exclusively in run.md. It checks: if `--autonomous` flag is present AND `vision.md` does not exist with a Judge-approved marker AND `--skip-human-gates` is not present → refuse with the prescribed message. Individual command files remain standalone-safe.

### Pitfall 6: profiles.json not updated for new Forge phase slots

**What goes wrong:** The new Forge internally dispatches agents for Research, Discuss, Plan, Execute, Verify sub-steps. If these need separate model routing (e.g., research uses perplexity-sonar, execute uses codex), the existing `forge` slot is insufficient.

**How to avoid:** For MVP, all sub-steps within a build phase use the `forge` slot's model. Only add new profile slots if the plan explicitly calls for per-substep routing. This avoids unnecessary profiles.json churn.

### Pitfall 7: discovery.md vs discovery/ directory collision

**What goes wrong:** The old Discover writes to `.seraphim/phases/{id}/discovery/external.md` and `discovery/internal.md`. The new Discover writes a single `discovery.md`. If run.md still checks for the old paths, it reports PHASE_OUTPUT_MISSING even after successful new Discover.

**How to avoid:** Update run.md's output verification table (Step 6c) to check for `discovery.md` instead of `discovery/external.md` + `discovery/internal.md`.

### run.md autonomous lockout check

```javascript
// Source: new logic in run.md Step 3 (after reading config)
const autonomousFlag = args.includes('--autonomous');
const skipHumanGates = args.includes('--skip-human-gates');
if (autonomousFlag && !skipHumanGates) {
  const visionPath = `${projectRoot}/.seraphim/phases/${phaseId}/vision.md`;
  const visionExists = fs.existsSync(visionPath);
  if (!visionExists) {
    // Check if vision has been Judge-approved
    process.stderr.write(
      'Autonomous mode blocked. Discover and Envision need human input — ' +
      'without it you get a pure AI project. ' +
      'Use --skip-human-gates if you really want that.\n'
    );
    process.exit(1);
  }
  // If vision exists, check for Judge Pass 1 approval marker
  const content = fs.readFileSync(visionPath, 'utf8');
  const markers = parseMarkers(content);
  const judgeApproved = markers.some(mk =>
    mk.type === 'PHASE_COMPLETE' && mk.phase === 'judge' && mk.mode === 'vision'
  );
  if (!judgeApproved) {
    process.stderr.write('Autonomous mode blocked: vision.md has not been Judge-approved yet.\n');
    process.exit(1);
  }
}
```

| Old Approach | New Approach | Impact |
|---|---|---|

| run.md: 6-phase linear sequence with one Judge invocation | run.md: Discover→Envision→Judge(vision)→Architect→Judge(arch)→Forge→Crucible + lockout gate | Pipeline now enforces human involvement |

## Open Questions

1. **discovery.md format — what replaces the old SERAPHIM markers?**
   - What we know: The new Discover writes a single `discovery.md` with research findings + 5-7 curated links.
   - What's unclear: Should discovery.md have a PHASE_START/PHASE_COMPLETE wrapper for pipeline verification? The old format had them.
   - Recommendation: Keep PHASE_START/PHASE_COMPLETE markers in discovery.md for run.md output verification consistency. Add a `SERAPHIM:DISCOVERY_LINKS count="N"` marker after the curated links section for machine-readable link count auditing.

2. **vision.md — how does Judge Pass 1 apply approved tweaks in-place?**
   - What we know: D-16 says "Updated vision.md (tweaks applied directly)."
   - What's unclear: Does judge.md rewrite the entire file with tweaks applied, or does it append a diff/patch section? Rewriting is cleaner but Judge must re-emit the full document.
   - Recommendation: Judge Pass 1 rewrites vision.md entirely with approved tweaks applied. It adds a `<!-- SERAPHIM:PHASE_COMPLETE phase="judge" mode="vision" approved_tweaks="N" rejected_tweaks="N" -->` marker at the end of the approved vision. This is the marker run.md checks for the autonomous lockout.

3. **architect-plans.md — what's the PLAN marker schema?**
   - What we know: Need machine-parseable plan boundaries for Judge Pass 2. Should mirror APPROACH marker structure to reuse existing parsing patterns.
   - What's unclear: Whether plans need sub-task lists or just high-level overviews at this stage.
   - Recommendation: Plans are high-level at this stage (architecture + tech stack + component structure + data model + implementation strategy). No sub-tasks. Schema: `<!-- SERAPHIM:PLAN id="plan-1" complexity="medium" approach_name="Event-sourced PostgreSQL" -->`.

4. **Forge's GSD cycle — does "Discuss" require persisting CONTEXT.md per build phase?**
   - What we know: D-27 says grey area discussions happen per build phase. D-29 says these are about implementation details only.
   - What's unclear: Whether the Forge writes a CONTEXT.md-style file per build phase (like GSD's discuss.md does) or handles it inline with a simpler "locked decisions" block in the forge log.
   - Recommendation: Write a lightweight `build-phase-{N}-decisions.md` file per build phase rather than a full CONTEXT.md. This gives the per-phase execute agent a locked decisions reference without imposing the full GSD discuss.md ceremony.
