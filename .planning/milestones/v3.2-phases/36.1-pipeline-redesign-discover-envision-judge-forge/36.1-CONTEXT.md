# Phase 36.1: Pipeline Redesign — Discover, Envision, Judge, Architect, Forge - Context

**Gathered:** 2026-04-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Redesign the full Seraphim pipeline flow: Discover (broad→focused web research), Envision (convergent — narrows scattered research into one unified vision), Judge (runs twice — once on vision, once on architecture), Architect (3 technical build plans from approved vision), Forge (GSD-style per-phase research→discuss→plan→execute→verify). Add autonomous mode lockout gate enforcing human involvement through Envision. Update `run.md` orchestrator for new two-pass Judge flow.

</domain>

<decisions>
## Implementation Decisions

### Discover (Wing I) — Redesign
- **D-01:** Uses Perplexity + SearXNG for real web research. No fake or training-data-only URLs.
- **D-02:** Rounds are broad → focused, but no hard cap. Human can go deeper, pivot to a different topic, or rabbit-hole entirely. No fixed round limit.
- **D-03:** After each round, AI presents findings + explicit prompt: "Go deeper on a topic? / New direction? / I'm armed, move to Envision." Human always chooses.
- **D-04:** Interesting links accumulate across rounds. At the end, AI + human collaboratively filter to the final 5-7 high-importance links (articles, Twitter threads, YouTube, podcasts, docs).
- **D-05:** Bad search results: AI auto-retries once with refined query. If still poor, surfaces the issue and asks human for direction.
- **D-06:** Final output: `discovery.md` with research findings + curated 5-7 links. This arms the human for Envision.

### Envision (Wing II) — Convergent Redesign
- **D-07:** Envision is a CONVERGENT phase. It takes all the scattered discovery input (topics, approaches, thoughts, links) and narrows them down into ONE solid unified project vision. Not multiple alternatives — one clear direction.
- **D-08:** Uses a scientific approach to narrow abstract thoughts: categorize inputs, identify themes, surface conflicts, resolve tensions, distill into clear statements.
- **D-09:** Requires its own research to fill knowledge gaps discovered during convergence. If the discovery surfaced questions that need answers before the vision can solidify, Envision researches those specific gaps.
- **D-10:** AI proposes 6-10 discussion topics derived from the discovery material. Human reorders, adds, or removes topics before discussion starts.
- **D-11:** Each topic is discussed conversationally. After each topic, AI evaluates whether there's enough clarity to write the vision. When threshold is hit, offers to draft.
- **D-12:** Output: `vision.md` containing project goals, what it does, how it does it, constraints, aspirations, notes, and the general outline plan. ONE vision, not alternatives.

### Judge — Pass 1: Vision Review (Wing III, first invocation)
- **D-13:** Judge reviews `vision.md` and surfaces things that might need tweaking — gaps in logic, unrealistic assumptions, missing constraints, internal contradictions.
- **D-14:** This is a LIGHT pass — not adversarial stress-testing. The Judge is helping refine, not trying to kill the vision.
- **D-15:** Each suggested tweak is presented to the human who approves or disapproves it individually. Human has final say on every change.
- **D-16:** Output: Updated `vision.md` (the tweaks are applied directly). The vision is now final and approved.

### Architect (Wing IV) — Technical Divergence
- **D-17:** Architect reads the FINAL `vision.md` — NOT `judgment.md`. The vision is the spec. The judgment was a refinement step that already updated the vision.
- **D-18:** Architect creates 3 different technical build plans/approaches to achieve the project vision. These are implementation alternatives — same goal, different technical paths.
- **D-19:** AI decides plan count based on complexity (2-4 range: simple=2, medium=3, complex=4). Default is 3.
- **D-20:** Each plan covers architecture, tech stack choices, component structure, data model, and implementation strategy. These are technical, not conceptual.

### Judge — Pass 2: Architecture Review (Wing III, second invocation)
- **D-21:** Judge reviews the Architect's 3 technical plans. This IS adversarial — stress-testing each approach for feasibility, scalability, maintainability.
- **D-22:** Judge either: (a) picks the best winner, (b) merges winning aspects from multiple plans, or (c) gives harder rules/parameters and sends back to Architect (max 1 loop).
- **D-23:** Output: ONE `blueprint.md` — the final merged/selected technical plan. This is the execution spec.
- **D-24:** `blueprint.md` must be written so precisely that even a local LLM can follow it blindly. The more precise, the better. Every decision locked, every file path named, every interface defined.
- **D-25:** `blueprint.md` is broken into build phases with their own build waves (GSD-style structure). Each phase has clear boundaries, dependencies, and success criteria.

### Forge/Executor (Wing V) — GSD-Style Execution
- **D-26:** Forge reads `blueprint.md` and executes each build phase sequentially.
- **D-27:** For EACH build phase in the blueprint, the Forge runs a full GSD cycle:
  1. **Research** — External + internal research specific to that phase's technical domain
  2. **Discuss** — Surface grey areas to the human for each phase (GSD-style grey area discussion). Human locks implementation decisions before execution.
  3. **Plan** — Create detailed task plans with acceptance criteria for that phase
  4. **Execute** — Run tasks in waves (separate agents, fresh context per wave). Wave-based parallel execution with dependency resolution.
  5. **Verify** — Verify phase completion against its success criteria before moving to next phase
- **D-28:** Each phase spawns separate agents with brand new context. No context bleed between build phases.
- **D-29:** The Forge does NOT re-decide architecture — it executes what the blueprint specified. Grey area discussions are about implementation details (how to build), not what to build.

### Autonomous Mode Lockout
- **D-30:** Autonomous mode cannot be enabled until Envision is complete (vision.md exists and has been Judge-approved). If attempted before, pipeline refuses with: "Autonomous mode blocked. Discover and Envision need human input — without it you get a pure AI project. Use --skip-human-gates if you really want that."
- **D-31:** Override available via `--skip-human-gates` flag. Produces loud warning but allows it. Explicit opt-in to pure AI.
- **D-32:** Even with autonomous mode on, the Forge's per-phase grey area discussions are skipped (auto-selected). The human chose to trust the AI for implementation details.

### Pipeline Orchestrator (run.md) Updates
- **D-33:** `run.md` must be updated to support the two-pass Judge flow. The phase sequence becomes: Discover → Envision → Judge(vision) → Architect → Judge(architecture) → Forge → Crucible.
- **D-34:** Judge needs a `--mode` parameter: `--mode vision` for Pass 1 (light review) and `--mode architecture` for Pass 2 (adversarial + blueprint creation).
- **D-35:** The Architect→Judge→Architect loop (max 1) is managed by `run.md`, not by Judge itself.

### Claude's Discretion
- Internal prompt structures for each wing's subagent dispatch
- Search query construction for Perplexity/SearXNG
- Discussion topic generation heuristics in Envision
- Complexity assessment for architect plan count (2-4)
- Forge wave decomposition strategy within each build phase
- Blueprint formatting and level of detail (as long as it meets "local LLM can follow it" bar)

<specifics>
## Specific Ideas

- The 5-7 links should be diverse sources: not all articles, mix in Twitter threads, YouTube, podcasts, docs
- Envision should feel like a founder narrowing vision with a trusted advisor, not filling out a form
- The Judge vision review should feel like a gentle "have you considered..." not an interrogation
- The Judge architecture review should be genuinely adversarial — try to break each plan
- blueprint.md precision bar: "a local LLM model can follow it super accurately"
- The Forge grey area discussions should feel quick and focused, not ceremonial — the big decisions were already made
- The autonomous lockout message should be genuinely opinionated, not corporate-polite

</specifics>
